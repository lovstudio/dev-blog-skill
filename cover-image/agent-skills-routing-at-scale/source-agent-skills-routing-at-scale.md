# 大目录，小激活集：Skills 增长后的 Agent 路由与用户发现

当 Agent 只有三五个 Skills，模型靠名称和描述通常就能选对。等目录增长到几十、几百个以后，问题会突然变得不同：Agent 开始漏选、错选，用户面对一排相似卡片，也不知道它们究竟差在哪里。

2026 年 7 月 13 日查看 [LovStudio Agent Hub](https://lovstudio.ai/agent) 时，页面共有 26 个条目，其中已经同时出现 `Contract Review` 和 `Contract Review Pro`。26 并不是一个危险数字，但两个语义接近、商业档位不同的能力同时进入候选池，已经暴露了真正的问题：**规模化 Skill 系统的瓶颈不是库存，而是路由。**

## 一开始容易想到的三个答案

最直觉的解法通常有三个：增加分类、限制 Skill 总数，或者给目录加一个向量搜索。

这三个方向都有用，但都不完整。

- 分类能帮助人浏览，却不能区分两个描述相近的 Skill。
- 限制总数会牺牲长尾能力，真正需要控制的是一次请求中同时竞争的候选数。
- 向量搜索能缩小范围，但相似描述往往会把错误近邻一起召回；没有负向样本和重排，它甚至可能更稳定地选错。

因此，这次核验没有把问题理解成“市场里最多能放多少 Skills”，而是拆成了三层：后台可以收录多少、本轮应该激活多少、用户到底需要看到什么。

## 关键转折：总目录和当轮候选不是一回事

[Anthropic 的企业 Skills 指南](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)直接指出，每个 Skill 的名称和描述都会在系统提示中竞争注意力；同时启用太多，模型可能选错，也可能完全漏掉。官方给出的处理方式不是停止扩充目录，而是按任务或角色路由到较小的 Skill 集合，并通过共存测试决定收窄描述、合并或弃用。

[OpenAI Skills API](https://developers.openai.com/api/docs/guides/tools-skills)与 [MCP 客户端最佳实践](https://modelcontextprotocol.io/docs/develop/clients/client-best-practices)体现的是同一套架构：启动阶段只暴露紧凑的名称和描述，命中后再加载完整说明、参数和资源。完整能力可以很多，但当轮上下文必须克制。

这可以概括成一句话：

> 大目录，小激活集；用户选择目标，Agent 选择 Skill。

## 一套可落地的分层路由

适合 LovStudio 这类 Skill 市场的执行链路是：

```text
用户目标
  ↓
权限、项目、平台、文件类型、价格权益、风险过滤
  ↓
关键词 + 语义混合召回
  ↓
少量候选重排，并保留“都不适用”
  ↓
高置信度：自动选择
候选接近：解释差异或追问一个问题
  ↓
加载完整 SKILL.md、依赖和工具
  ↓
执行 → 记录 → 回归评测
```

这里需要明确区分四种视图：

| 对象 | 应该看到的内容 |
| --- | --- |
| 用户 | “合同审查”“发布文章”这样的任务工作流 |
| 路由器 | 简短、结构化、互相可区分的 Skill 卡片 |
| 执行 Agent | 命中后加载的完整说明、工具和参考资料 |
| 管理者 | 全量目录、版本、负责人、风险、评测和弃用状态 |

用户不应该先理解 Skill、工具、MCP 和插件的技术区别，才能完成工作。首页更适合问“你想完成什么”，技术名称、版本、依赖和价格放在第二层解释。

## Description 不是简介，而是路由规则

[Agent Skills 规范](https://agentskills.io/specification)要求 description 同时说明“做什么”和“什么时候使用”。这还不够。一个可治理的 Skill 卡至少应该包含：

```text
stable_id / workflow_id / variant
用户显示名
what / when / not_when
正向、负向和近邻示例
输入前提与输出
权限、副作用和风险
平台、工具与价格权益依赖
owner / version / status / last_eval
```

[OpenAI 的元数据优化指南](https://developers.openai.com/apps-sdk/guides/optimize-metadata)建议用直接、间接和负向提示词评测选择精确率与召回率。这一点很重要：如果只测试“应该触发”的请求，几乎所有宽泛描述都会看起来不错；真正暴露问题的是“不该触发”和“与近邻 Skill 容易混淆”的请求。

同行评审研究也支持这个方向。[ToolScope](https://aclanthology.org/2026.acl-long.1573/)发现，名称与描述重叠会造成明显的工具选择歧义；[ToolRet](https://aclanthology.org/2025.findings-acl.1258/)在四万多个工具上的实验表明，通用检索器并不足以稳定解决专业能力召回，检索噪声会传导到最终任务成功率。它们研究的主要是工具而非完整 Skill，因此具体数字不能直接照搬，但“重叠治理、困难负样本和动态候选集”的方向具有很强的可迁移性。

## LovStudio 可以先改哪一步

最值得先做的不是重构整个市场，而是从语义冲突最明显的条目开始。

以 `Contract Review` 和 `Contract Review Pro` 为例，更合理的产品表达是一个“合同审查”工作流，标准版与专业版作为 `variant`。系统先根据用户权益和任务风险过滤可用版本，再进入语义选择。商业套餐不应该作为两个近义 Skill 去争抢同一个用户意图。

页面侧可以同步做三件小事：

1. 增加“描述你想完成什么”的意图搜索，而不只是分类筛选。
2. 卡片优先展示产出、典型输入、不适用场景、权限和副作用。
3. 相似能力最多比较两三个，并明确推荐理由；不要把整张技术目录交给用户自行排错。

## 评测决定什么时候继续增加

行业里没有可信的统一硬上限。Claude API 的每次最多 8 个 Skills、工具侧常见的 10 或 20 个建议，都属于具体平台约束或经验值，不能写成“超过这个数字 Agent 就会失效”。

更可靠的做法是为每个新 Skill 准备四类真实请求：

- 应该触发；
- 不应该触发；
- 与相邻能力容易混淆；
- 信息不足、无需 Skill 或需要多个 Skills。

然后持续记录首选准确率、前几名召回率、误触发、用户切换、澄清率、任务成功率、延迟和上下文成本。新增 Skill 如果让旧 Skill 的命中率下降，就应收窄边界、调整路由或合并，而不是继续堆描述。

## 最后留下的工程判断

Skill Marketplace 可以持续增长，但 Agent 每次看到的菜单必须很小；用户看到的则应该是结果明确的工作流。

分类和命名空间解决的是浏览与标识，渐进披露解决的是上下文成本，检索解决的是候选缩小。真正把它们连成系统的，是确定性过滤、重排、置信度门槛、人工审批和持续评测。缺少最后这层治理，再漂亮的 Skill 市场最终也会变成一张越来越难用的工具清单。
